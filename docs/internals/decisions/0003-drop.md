# 0003 — Drop: files onto the notch, actions from extensions

Status: accepted for 0.14.0 (2026-11-13). Open questions answered at the end.

## Problem

People drag files to the top of the screen to keep them for a moment, send them to a phone or open them in another app. The notch is where the pointer already goes. NotchNotch should catch the drag, and anyone should be able to add what happens to the files, the same way anyone can add an activity.

Two things make this harder than an activity:

- **Speed.** Zones have to appear while the pointer is still moving. The runner is another process that talks JSON, so the app can't ask an extension on every mouse move.
- **Trust.** A file path tells an extension where the person keeps things, and reading a file is reading their data. An extension that only sends files somewhere shouldn't get either.

## Decision

The app owns the drag. Extensions declare **drop zones** in their tree, and receive the dropped files as **handles** when the person lets go on their zone. What an extension can do with a handle is limited to what the app does for it, unless the extension has the `file-read` permission.

### Drop zones are declared, not asked for

```tsx
<DropZone id="keep" title="Shelf" icon="tray" accepts={["public.item"]} multiple
          onDrop={(files) => keep(files)} />
```

- `DropZone` is a top-level element, a sibling of `Activity` and `Settings`. An extension may render up to 2; they can come and go with state (a "Send to iPhone" zone only while the phone is reachable).
- The tree is already in the app as part of the snapshot, so the app draws zones the moment a drag starts, with no round trip.
- `accepts` is a list of UTIs. The app shows a zone only when every dragged item conforms to one of them. `multiple: false` hides it for more than one item.
- `title` says what happens ("Shelf", "AirDrop", "Compress"); while hovered, the app adds the count ("Drop to keep 3 files").
- Older apps leave out the unknown node type (0.11 and later), so a bundle with a `DropZone` still runs there without it.

### The app draws the drag

1. **Noticing a drag.** macOS doesn't announce one. The app watches the drag pasteboard's change count and the pointer. When a drag is in progress and the pointer comes within ~60 pt of the notch, the notch opens to the Drop view. The panel is then a real `NSDraggingDestination` for the drop itself.
2. **Zones.** Only zones that accept every dragged item, in the person's order (Settings → Notch → Drop, as in Home). Up to four, the same height as Home's tiles; more than four makes the last a More zone that opens the full list in place.
3. **Hover.** The zone under the pointer grows and takes its extension's accent; the others dim. No zone accepts the files: the notch says so and closes when the drag leaves.
4. **Drop.** The app turns the files into handles, sends one `drop` event to that extension, and closes the Drop view. A zone with `opens` names one of its activities; the app opens it right after the drop and keeps it open until the person closes it, so they can act on what they dropped without finding it in Home. Without `opens`, the extension answers as it likes, usually with a peek.

### Text and links

A zone that accepts `public.url` or `public.plain-text` also takes what a browser or editor drags: a link, or selected text. They arrive as values, not handles, since they're what the person chose to drag:

```ts
type DropItem = { kind: "file"; file: FileHandle } | { kind: "url"; url: string; title?: string } | { kind: "text"; text: string };
```

Text is cut at 64 KiB. A link to a file on disk (`file://`) arrives as a file handle, never as a path.

### Handles, not paths

```ts
interface FileHandle { id: string; name: string; type: string; size: number; kind: "file" | "folder" }
```

- `id` is opaque. The app keeps a security-scoped bookmark for it, per extension, and resolves it when the extension asks for an action. Handles survive restarts, so they can be stored with `useStoredState`.
- `files.release(ids)` drops bookmarks the extension no longer needs. Uninstalling an extension releases all of its handles.
- An extension never sees a path.

### The `files` API

Host-performed actions, no permission needed beyond having the handle:

| Call | Does |
| --- | --- |
| `files.airDrop(ids)` | AirDrop sheet (`NSSharingService`) |
| `files.open(ids, app?)` | Opens with the default app, or one the person picks |
| `files.reveal(ids)` | Selects them in Finder |
| `files.preview(ids)` | Quick Look |
| `files.thumbnail(id)` | A small PNG data URL of the file's real thumbnail |
| `files.copy(ids)` / `files.move(ids)` | Into a folder the person picks in an open panel |
| `files.share(ids)` | macOS's Share menu beside the pointer (AirDrop, Messages, Mail, …) |
| `files.openWith(ids)` | A menu of the apps that open them, beside the pointer |
| `files.copyToClipboard(ids)` / `clipboard.copy(text)` | The clipboard, as Finder's Copy |

With the `file-read` permission (shown in the install review as "Reads the files you drop on it"):

| Call | Does |
| --- | --- |
| `files.read(id, { as: "text" \| "base64", offset, limit })` | Contents, up to 144 KiB per call; `offset` reads a large file in parts |
| `files.save(name, data)` | Writes a result of up to 144 KiB into a folder the person picks; returns a new handle |

Every message between an extension and the app is at most 256 KiB, which sets the 144 KiB per call.

### Thumbnails are macOS's own

Every file shows what Finder shows: `QLThumbnailGenerator` gives the real preview (a photo, a PDF's first page, a video frame), and where there is none, the file's icon from `NSWorkspace`, so a folder is the macOS folder, an app its own icon, a document its type's icon. Never a colored placeholder. Thumbnails are made in the app, cached per handle and size, and drawn natively; an extension gets one as a data URL only through `files.thumbnail`.

### `FileItem`

A reading component for showing a handle: its thumbnail, name and size. The app draws it natively, so it can be **dragged back out** of the notch to Finder, Mail or any app. Allowed in expanded content and in tiles (without the drag).

### Selection

`FileGrid` selects like Finder when the extension passes `selected` and `onSelect`: a click selects one, ⌘ adds one, ⇧ adds a range, any click on a selected file lets go of it (the notch has no empty space to click, and a file caught in a range by mistake comes out alone), a double-click opens. The grid draws the click at once and the extension's `selected` catches up. Dragging a selected file takes the whole selection; each file's menu (Quick Look, Open, Open With, Show in Finder, Copy, Share, and Remove with `onRemove`) acts on the selection it's in. `onDragOut` hears which files landed somewhere. A `ListItem` with `drag` drags its text or link out.

### Shelf

A built-in extension, like Music:

- One zone that accepts anything. Dropped files are kept as handles; "Keep a copy" (a preference) copies them into the app's Shelf folder instead, so they survive the original being moved.
- An `Activity` that's always `paused`: a glance in Home with a tile showing the count and the first thumbnails, never holding the wings.
- Expanded: the files in a `FileGrid` that selects, and a bar that acts on the selection or on every file: Remove or Clear, Copy, Open With, Quick Look, Share. Links and text as rows with Copy, and they drag out.
- "Remove files after dragging them out" (a preference) empties the Shelf as files leave it.
- A short peek after a drop ("3 files kept").

### First Store drop actions

AirDrop, Open With and Quick Look as three small Store extensions, each a few lines on top of `files`. They prove the API and need no permission.

## Rules

1. The app never runs extension code during a drag; zones come from the last snapshot.
2. A handle is valid only for the extension that received it.
3. Without `file-read`, an extension learns names, types and sizes, and nothing else about the files.
4. Every action that writes asks the person where, through the app's own open/save panel.

## Answered

- **Folders** are one handle (`kind: "folder"`): share, open, reveal, copy and move work; `read` refuses them. Listing a folder's contents waits for a reason.
- **Text and links** are in 0.14 (above).
- **Dragging out**: from the open Shelf, each file drags on its own; from the Shelf tile in Home, dragging the stack of thumbnails drags every file at once, and a click still opens the Shelf.
