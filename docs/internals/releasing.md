# Releasing

## Local build

```sh
pnpm release
```

Builds universal (arm64 + x86_64) release binaries, packages `dist/NotchNotch.app` and creates `dist/NotchNotch-<version>.dmg` and the update archive `dist/NotchNotch-<version>.zip`. With `SPARKLE_PRIVATE_KEY` set it also signs the archive and writes `dist/appcast.xml`.

## Automatic updates

Installed copies update themselves with [Sparkle](https://sparkle-project.org). Only release builds (`pnpm release`) contain the feed URL and public key; `pnpm dev` and CI builds never check for updates.

- **Feed:** `https://raw.githubusercontent.com/NotchNotch/notchnotch/appcast/appcast.xml`, on the `appcast` branch. The **Publish update feed** workflow updates it when you publish a release, never for a draft, so users are only offered downloads that exist.
- **Signature:** every update archive is signed with an EdDSA key. The public key is committed in `apps/macos/SparklePublicKey` and embedded as `SUPublicEDKey`. Sparkle rejects an archive whose signature doesn't match, so ad hoc code signing is fine: when the EdDSA signature is valid, Sparkle accepts a new ad hoc signature as long as it is itself valid.
- **Version:** Sparkle compares `CFBundleVersion`, which the release workflow sets to its run number. Releases built locally default to build 1 and should not be published as updates.

The key pair was created once with `node scripts/sparkle.mjs keys`. The private key lives outside the repository in `~/.config/notchnotch/sparkle-ed25519-private-key`; keep a backup in your password manager. **If it is lost, installed copies can never be updated again** and users must download the next DMG by hand. Give it to the release workflow once:

```sh
gh secret set SPARKLE_PRIVATE_KEY < ~/.config/notchnotch/sparkle-ed25519-private-key
```

`release.mjs` refuses to sign with a private key that doesn't match the committed public key.

## Signing options

| `NOTCHNOTCH_SIGN_IDENTITY` | Result |
| --- | --- |
| unset | Ad hoc. Works, but every new build has a new signature, so macOS asks users again for Automation and Calendar access after each update. |
| `NotchNotch Self-Signed` | Free and stable. Permissions survive updates. Gatekeeper still treats the app as unnotarized (users choose **Open Anyway** once). |
| `Developer ID Application: …` | Paid Apple Developer Program. Adds a secure timestamp; with `NOTCHNOTCH_NOTARY_PROFILE` the DMG is notarized and stapled, so it opens without warnings. |

Create the self-signed identity once (it asks for your password to trust it for code signing):

```sh
scripts/create-signing-identity.sh --export ~/notchnotch-signing.p12
NOTCHNOTCH_SIGN_IDENTITY="NotchNotch Self-Signed" pnpm release
```

The script prints the `gh secret set` commands that let the release workflow sign with the same identity. Keep the `.p12` private, and keep using the same identity: a new one resets users' permissions once.

With any real identity, the app, `ExtensionRunner` and bundled helpers are signed inside-out with the hardened runtime and these entitlements:

| Target | Entitlements |
| --- | --- |
| `NotchNotch.app` | Apple Events, Calendars. TCC attributes the bundled helpers to the app that contains them |
| `ExtensionRunner` | `cs.allow-jit` for JavaScriptCore |
| `Sparkle.framework` | None (`Autoupdate` and `Updater.app` are signed first; its XPC services are removed because the app isn't sandboxed) |
| `MusicAdapter.app` | Apple Events |
| `CalendarAdapter.app` | Calendars |

## Checklist

1. Update the version in `package.json` (the app version is derived from it) and move **Unreleased** in `CHANGELOG.md` to the new version.
2. `pnpm check`
3. Commit, then tag: `git tag v<version> && git push origin v<version>`.
4. The **Release** workflow builds the DMG and creates a draft pre-release on GitHub. Without secrets it is ad hoc; the optional secrets listed at the top of `.github/workflows/release.yml` add a stable signature or notarization.
5. Install the DMG on another Mac (Open Anyway), connect Music and Calendar, and publish the draft. Publishing runs **Publish update feed**, which puts the release's `appcast.xml` on the `appcast` branch; installed copies see the update within a day, or at once with **Check for Updates…**.

The app icon is generated by `swift scripts/make-icon.swift <dir>.iconset` followed by `iconutil -c icns`.
